# Token 密度标定：拿官方真实数据定「往高报」的系数（2026-09-23）

**为什么这个文件存在**：用户指令（第五轮）——「计费token的问题--关于真实计费，做不到就保险往高报」
「我记得有人统计过中英文对于 dsv4flash 密度官方计算，或者你拿着官官方的真实数据验证增加」。
即：**往高报可以，但系数必须有真实依据**，不能拍脑袋。

本轮先取官方文档的平均值，再用**官方端点实测**验证，最后用一个「每类都不低于实测」的可行解
替换旧系数。全部读数与命令都在本文里，可原样复算。

> 口径纪律：凡「实测」给出样本、字符构成与官方返回的 `usage`；凡「拟合」给出可行域与判据；
> 凡「选值」说明为什么选它、以及它带来的副作用。**不做推测性归因**。

---

## 1. 官方文档给的平均值

[DeepSeek API Docs · Token 用量计算](https://api-docs.deepseek.com/quick_start/token_usage) 逐字：

- 「通常 1 个中文词语、1 个英文单词、1 个数字或 1 个符号计为 1 个 token」
- **1 个英文字符 ≈ 0.3 个 token**
- **1 个中文字符 ≈ 0.6 个 token**

这是**平均数**，不是分类单价——所以它只能当量级参照，不能直接当系数（下面实测会显示：
纯英文散文实际 0.23，比文档的 0.3 低；而源码 0.37、数字与符号 0.68，都比文档的分类高）。

## 2. 实测方法（`package/dsh-webcode-bridge/.tmp/probe-token-density.mjs`）

- 端点：`https://api.deepseek.com/anthropic/v1/messages`（本机 DSH 的 `llm-deepseek`
  适配器用的就是这条 Messages 兼容路由），`model=deepseek-chat`，`max_tokens=1`。
- 凭据：本机 DSH 凭据库里的 `DEEPSEEK_API_KEY`，**只进请求头，不打印**。
- 六类样本：纯中文技术散文 / 纯英文技术散文 / 中英混排 / 源码-JS / JSON 协议 / 数字与符号。

### 2.1 一个必须先修的测量陷阱：上下文缓存

第一版标定把「同一段 JS 文本」跑出 **277** 与 **149** 两个数（相差 1.86 倍）。
根因是 DeepSeek 的**自动上下文缓存**：命中的前缀不计入 `input_tokens`，而记进
`cache_read_input_tokens`。同一段文本第二次请求时前缀命中，于是 `input_tokens` 只剩未命中的尾巴。

处置（双保险，已在探针里）：

1. 每次请求给样本加一枚**随机 nonce 前缀**，让两次请求的字节不完全相同；
2. 真值一律取 `input_tokens + cache_read_input_tokens`（即便命中也按全量算）。

> 这条值得单独记：**没有它，整组系数都是错的**。它也是本项目反复写的那条纪律的又一例——
> 「读数的取得条件必须写进读数本身」。

## 3. 实测结果（六类样本）

| 样本 | 字符 | CJK | 非 CJK | 官方 `input_tokens` | 密度 |
| --- | --- | --- | --- | --- | --- |
| 纯中文技术散文 | 140 | 130 | 10 | **104** | 0.74–0.80 tok/字 |
| 纯英文技术散文 | 410 | 0 | 410 | **96** | 0.234 tok/字符 |
| 中英混排 | 248 | 30 | 218 | **76** | — |
| 源码 JS | 759 | 0 | 759 | **283** | 0.373 tok/字符 |
| JSON 协议 | 448 | 0 | 448 | **117** | 0.261 tok/字符 |
| 数字与符号 | 176 | 0 | 176 | **120** | 0.682 tok/字符 |

（六次请求的原始 `usage` 逐条打印在探针输出里；机读副本落 `.tmp/token-density.json`。）

## 4. 旧系数在同一批样本上的表现（这就是要改的理由）

旧口径 = CJK 0.7 + 其余 0.25（未计末尾余量）：

| 样本 | 实测 | 旧估 | 比值 |
| --- | --- | --- | --- |
| 纯中文 | 104 | 93.5 | **0.90×（低估）** |
| 纯英文 | 96 | 102.5 | 1.07× |
| 中英混排 | 76 | 75.5 | 0.99×（贴线） |
| **源码 JS** | 283 | 189.8 | **0.67×（低估 33%）** |
| **JSON** | 117 | 112.0 | **0.96×（低估）** |
| **数字与符号** | 120 | 44.0 | **0.37×（低估 63%）** |

**结论有一条与直觉相反、必须写清**：用户怀疑的是中文，但中文那侧旧值本来就偏高
（0.90× 是低估，加上 10% 余量后约为 0.99×，基本贴合）；**真正被严重低估的是
代码、JSON 与标点符号——恰好是编码 agent 的主要流量**。根因是旧实现把
「英文散文」与「代码/符号」混成同一个 0.25，而两者实测差 2.9 倍。

## 5. 拟合与选值

把字符分成三类（CJK / ASCII 字母与空白 / 其余 ASCII），在
cjk∈[0.60,1.00]、word∈[0.20,0.40]、other∈[0.45,0.85] 的网格上搜索同时满足
**六个样本全部 ≥ 实测**（`under = 0`）的组合，再取**最大超额最小**的那个：

| 类别 | 实测区间 | 选用系数 | 说明 |
| --- | --- | --- | --- |
| CJK | 0.74 | **0.75** | 略高于实测 |
| ASCII 字母/空白 | 0.23 | **0.30** | 高于实测与官方文档值 |
| 其余 ASCII | 0.26–0.68 | **0.70** | 覆盖最高的一类；这正是旧的漏洞 |
| 余量 | — | **+10%** | 见下「为什么保留余量」 |

逐样本校验（含 10% 前的纯系数）：中文 1.02×、英文 1.31×、混排 1.21×、源码 1.03×、
JSON 1.59×、数字符号 1.00× —— **六类全部 ≥ 1.00×**，最坏 1.59×。

### 5.1 为什么还保留 10% 余量（而不是刚好贴住实测）

标定对象是 **API 侧 `deepseek-chat`**，而桥驱动的是**网页版**模型，其分词器未公开；
样本也没覆盖全部文本形态。用户口径是「做不到就保险往高报」，因此余量是**明确标注的猜量**，
不是校准结果。宁可多报，不可少报。

## 6. 落到哪（单一真相）

- 系数常量：`lib/metrics.js` 的 `TOKEN_DENSITY`（**唯一一处**）。
- 所有出口共用 `estimateTokens`：DSH 的 `usage` 事件、OpenAI 兼容前端的
  `prompt_tokens/completion_tokens`、右栏 TPS 统计、发送前预算闸 `checkContextBudget`。
  改这一处即全链路生效，不存在「某个出口还按旧系数报」的可能。
- 固定开销：`usageFixedOverheadTokens`（默认 2048），见 §7。

## 7. 输入侧的固定开销（网页自己注入的上下文）

用户原话：「要：每轮加一笔固定开销」。补的是这个缺口：桥报的 `inputTokens` 一直是
「我发出去的文本」，而网页那一侧的上下文还包含**它自己的系统提示、界面框架、站点前言**——
这些永远不经过桥，读数因此系统性偏低。

**实现上按「一次性偏移」计入，而不是逐轮累加**，理由：网页自己的系统提示在上下文里
只有**一份**（每轮重新 prefill ≠ 每轮多一份）。累加进累计值会重复计数、把压缩压力虚推上去——
用户要的是「不低估」，不是「虚高」。无会话键的单轮本身就是一份完整上下文，因此那里也是**一份**。

2048 是上界猜值：网页不公开自己的系统提示。唯一能实测它的办法是
[`2026-09-23-longrun-rounds-3-4.md`](2026-09-23-longrun-rounds-3-4.md) §3.6 的对账探针 D3
（读回 `POST /__webcode/history` 与桥的累计相比）。在那之前，读数里**必须**把这一项说成猜值。

## 8. 副作用（要一起认）

1. 同一段文本的 token 读数比 0.19.3 之前**普遍偏高**（源码约 +40%、JSON 约 +60%、
   数字符号约 +170%），因此**上下文压力与 DSH 压缩触发点都会变早**。
   这与「我要真实长上下文」存在拉扯：口径变保守 = 更早压缩。窗口声明是另一个独立的旋钮
   （`contextWindowBySite`），不要用「调大声明」去抵消这里的保守——那是把两个问题混成一个。
2. 右栏 TPS 也会跟着变（分子是估算 token）。它的用途是**相对速度比较**，方向不变。

## 9. 未证实项

1. 标定用的是 **API 侧 `deepseek-chat`**；网页版模型的分词器未公开，两者可能不同。
2. 六类样本**不是**穷尽抽样；emoji、其它语言、超长单 token 串未覆盖。
3. 2048 的固定开销是**猜值**，没有实测依据（§7 给了实测办法）。
4. 没有做「改成新系数后，模型真正消费的 token 是否更接近读数」的配对实验——
   那需要网页端返回真实 usage，而它至今不返回。
