# 长跑健全性：两轮完整思考（2026-09-23）

**性质**：本文是**纯思考记录**，按用户要求「不输出任何代码，只是文档记录你的思考」，
且要求「完整两轮」。因此它有两轮，各自**独立走完**（观察 → 归因 → 反证 → 结论）。
第二轮不是第一轮的补充说明，而是**换一个起点重来**，并显式对照第一轮。

**为什么值得两轮**：一轮思考容易停在「找到最显眼的那个问题」。长跑失效的特征
恰恰是**多个独立机制同时退化**，只修最显眼的那一个，下一次会在另一个地方断。
第二轮的职责是**换一个切面**，看第一轮的结论是否仍然成立。

**约束**：本文不新增代码、不改代码。所有引用都是已存在的文件与已测得的读数。
读数来源见 [`2026-09-23-dsh-longrun-and-compaction.md`](2026-09-23-dsh-longrun-and-compaction.md)
与 `doc/long-term-issues.md`。

# 第一轮：从「什么东西会杀死一个长会话」开始

## 1.1 起点：不预设病因，先列出全部致死路径

一个 DSH 会话要连续跑几小时到几天，它必须同时活着穿过**四层**，任何一层断了
都表现为「会话死了」，但根因完全不同：

| 层 | 谁在管 | 断了的症状 |
| --- | --- | --- |
| 宿主进程 | `dsh web` 那个 Node 进程 | 界面整个没了 |
| 会话状态 | `dsh-session` + 持久化 | 界面在，历史丢了 |
| 上下文预算 | `dsh-compaction-basic` + token meter | 跑着跑着报错/变傻 |
| 网页那一侧 | 桥（`lib/browser-driver.js`） | 桥还活着，但网页会话丢了 |

本项目的全部注意力历来在第四层——因为前三层是官方的、被别处测过，而第四层
**只有这个项目在管**。这个分工是对的，但它有一个盲区：**当问题出在第三层时，
第四层的日志会看不出异常**。

## 1.2 核心发现：第三层从来没被真正行使过

真机读数（304 份会话、272 份投影缓存）：

- `compaction/*` 事件**零命中**；
- 历史最高压力 **59.4%**（594,000 / 1,000,000），阈值是 80%；
- 达到 60% 的会话数：**0**。

**这条读数的意义不是「压缩坏了」，而是「压缩这条安全网从未被验证过」。**
它可能完全正常，也可能一触即碎——现有数据**无法区分**这两种情况。

这是一个比「压缩没触发」严重得多的结论。安全网的价值在于**它接得住**，
而一个从未承重的安全网，其可靠性是**未知**，不是「好」。

## 1.3 为什么这件事在长跑里会真的咬人

短会话不会碰到它（压力到不了）。长会话**必然**碰到它，因为：

1. 会话越长，`surfaceTokens` 单调增长；
2. 阈值是固定的 800,000；
3. 所以**只要跑得够久，一定会跨过去**——这不是概率问题，是时间问题。

于是长跑的真实风险不是「压缩会不会触发」，而是**「第一次触发时会发生什么」**。
而第一次触发的现场，是一个已经跑了几小时、上下文极贵、极不想重来的会话。
**在最不该出意外的时刻，运行着一条从未运行过的路径。**

## 1.4 归因：为什么从没跑到 80%？

三个候选，逐个验证：

**候选 A：会话都太短。** 部分成立。823 个 turn 分布在 304 个会话里，均值 2.7 turn。
但最大的会话有 594,000 压力——那是长时间真实工作。所以不是「都短」，
而是「**最长的那个也还差 20.6 个百分点**」。

**候选 B：压力读数算错了（低估）。** 无法用现有数据排除，但**方向上不利**：
若读数是低估，真实压力更高，那更该触发——与观测相反。所以 B 不能解释「没触发」。

**候选 C：声明窗口过大。** 这条成立，且是**唯一的充分解释**：
声明 1M → 阈值 800k → 而真实工作规模在 400k–594k 区间。
阈值被推到了一个正常使用够不着的地方。

## 1.5 第一轮结论

> **长跑最脆的一环，是那条从未被行使的压缩路径。** 它的阈值（800k）由桥的
> 乐观声明（1M）决定，而真实工作规模到不了那里。于是它长期处于「看似存在、
> 实则未验证」的状态——这是长跑里最危险的状态：**你以为有安全网，
> 但没人知道它结不结实。**

**第一轮给出的行动方向**：不是「调小窗口让它频繁触发」（那会在真实长跑里
频繁中断），而是**制造一次受控的触发**，把这条路径跑一遍，拿到它的真实行为读数。

# 第二轮：从「桥怎么知道网页还活着」开始

## 2.1 换起点：不问谁杀死会话，问「桥凭什么相信网页」

第一轮从「致死路径」这个角度切入，落到压缩。第二轮换一个**完全不同的起点**：
长跑里桥做的每一个动作，都建立在若干**关于网页的假设**上。假设一旦不成立，
动作就会错，而错误可能**不报错**。

把桥的全部假设列出来，逐条问「它怎么被验证」：

| 假设 | 验证方式 | 失效时的表现 |
| --- | --- | --- |
| 输入框收下了完整提示词 | `PROMPT_TRUNCATED` 回读校验 | **会报错** |
| 网页会话还在（URL/历史可读） | `WEB_SESSION_LOST` + URL 自愈 | **会报错/提示** |
| 这一轮回复已收全 | 收束原因（`finished`/`partial-wip-settled`/…） | **会提示** |
| 网页发出的调用形状可解析 | `parseAgentReply` + 诊断 | **会提示 + 自动续跑** |
| 网页还在跑这一轮（没卡死） | 超时 + 首个字节看门狗 | **会报错** |
| 模型「读了」我们发过去的内容 | **没有任何验证** | **静默** |

**前五条都有验证，第六条没有。** 这不是疏漏——它是**原理上无法验证**的：
网页模型是否「真的读了」一段文本，没有任何可观测信号。`attachTransport`
最多能证明上传被页面确认，不能证明模型读了内容
（`doc/PROMPT-ENGINEERING.md` §三 的未证实项第 3 条已记）。

## 2.2 第二轮的第一个发现：长跑里，不可验证项会累积

单轮里，「模型可能没读」影响有限——最坏这一轮答得差。
但长跑里它**累积**：

1. 每一轮都把当前上下文（在会话模式下是**首轮全文 + 增量**）发给网页；
2. 首轮全文里包含协议教学、工具清单、使用准则；
3. 如果模型对这些内容的「读取深度」随上下文变长而下降，那么**越到后面，
   格式约束越守不住**——而症状正是长跑里最眼熟的那一族：
   调用形状漂移、name 缺失、参数多挂一个对象。

这给了 `doc/long-term-issues.md` 里那 25 个「调用形状漂移」条目一个**统一的
可能解释**：不是模型随机犯错，而是**约束的注意力权重随上下文增长而衰减**。

**这是推断，不是读数。** 现有数据里没有「漂移率 vs 上下文长度」的配对观测。
但它可检验：把失败轮的 `surfaceTokens` 与漂移发生与否配对，看是否同向。
**这条应当被记为一个明确的待验假设。**

## 2.3 第二轮的第二个发现：桥的防护是「单轮视角」的

把 §2.1 表里那五条**有**验证的防护拿出来看，会发现它们有同一个形状：

> **每一条都在「这一轮」内闭环。** 收不到 → 报错；截断了 → 重试；漂移了 → 补发。

没有一条回答「**跨轮次**会怎样」。而长跑的定义就是跨轮次。具体缺口：

- **没有累积计数**：漂移发生了多少次、续跑救回来多少次、会话重建了几次——
  都散在日志里，**没有一个跨轮次的汇总**。于是「这个会话的健康度在下降」
  这个事实无法被自动发现，只能靠人翻日志。
- **没有退化判定**：如果续跑成功率从 90% 掉到 30%，桥照常每轮尽力救，
  但没有任何地方说「这个会话该重开了」。它会一直用高昂的代价维持一个
  正在变差的会话。
- **会话重建是「全有或全无」**：`WEB_SESSION_LOST` 要么整段重放成功，
  要么节流后交回提示。没有「只重放关键部分」的中间档。

## 2.4 反证：这些缺口真的会致命吗？

要防止「为了深刻而深刻」，逐条问「它有没有真的在真机里咬过人」：

| 缺口 | 真机证据 | 判定 |
| --- | --- | --- |
| 没有累积计数 | `web-restart*.log`、`reply-log` 都在，但需人工读 | **真实存在，未被证明致命** |
| 没有退化判定 | 节流（60s）正是缺它的补丁：没有退化判定，就用硬刹车防雪崩 | **已咬人，已用别的方式缓解** |
| 重建无中间档 | 0.16.4 的节流就是为它加的 | **已咬人，已缓解** |

**结论：三个缺口里，两个已经被「用别的方式缓解」，一个（累积计数）还完全空着。**
这不是说前两个解决了——而是说它们**已经被承认过**，而第三个还没被承认。

## 2.5 第二轮结论

> **长跑的第二个脆弱面，是桥的防护体系全部是「单轮闭环」。** 每一条都在
> 「这一轮」内自洽，但没有一条回答「跨轮次的健康度」。于是长跑里桥会
> **持续用同样的代价维持一个正在变差的会话**，而它自己不知道。
>
> 与第一轮的关系：第一轮说「安全网从未被验证」，第二轮说「**就算验证过，
> 桥也没有机制发现自己在变差**」。两条是**独立**的——第一轮修好（压缩验证过），
> 第二轮依然成立。这正是两轮思考的价值。

# 两轮对照与合并结论

## 3.1 两轮各自的落点

| | 第一轮 | 第二轮 |
| --- | --- | --- |
| 起点 | 什么会杀死长会话 | 桥凭什么相信网页 |
| 切面 | 四层架构 | 假设-验证矩阵 |
| 落点 | **压缩从未被行使** | **防护全是单轮闭环** |
| 性质 | 一条从未跑过的路径 | 一组从不汇总的信号 |
| 依赖第一轮吗 | — | **不依赖**（独立成立） |

## 3.2 共同结构

两轮独立走完，却指向同一个抽象形状：

> **长跑失效不来自「某个动作错了」，而来自「某个东西长期没被检查」。**
>
> - 第一轮：压缩路径**没被检查过**（从未触发）；
> - 第二轮：会话健康度**没被检查过**（从不汇总）。

桥的防护体系非常密（`long-term-issues.md` 里 25+ 条真机缺陷都已修），
但全部集中在「**当轮出错怎么办**」。两轮各自发现的，都是
「**没有任何一方在问：这东西现在还正常吗**」。

## 3.3 可检验的下一步（按用户约束，本文只记录，不实现）

1. **验证压缩路径**：制造一次受控的、超过 80% 压力的会话，观察
   `compaction/start` → `compaction/summary` → `compaction/end` 是否完整闭环、
   摘要质量如何、之后会话是否正常继续。
2. **验证漂移-上下文相关性**：把历史失败轮与 `surfaceTokens` 配对，
   检验 §2.2 那个假设。
3. **补跨轮次健康度**：一个跨轮次的计数与退化判定（本文只提出，不设计实现）。

## 3.4 未证实项（不许当结论用）

1. §2.2 的「注意力衰减」是**推断**，无配对读数。
2. §2.3 的「没有跨轮次汇总」是基于**读现有日志与代码的观察**，
   没有穷尽检索是否存在某个未发现的汇总点。
3. 两轮都**没有**做过正向实验；所有结论都是**观察性**的。
4. 「制造受控触发」在真机上的可行性未验证——桥的 `CONTEXT_WINDOW_EXCEEDED`
   可能在压力到 80% **之前**先拦下（它拒的是 `ratio > 1`，理论上不冲突，
   但**没有实测**）。

## 3.5 一句话

> 长跑的对手不是「出错」，而是「**安静地不再正常**」。
> 两轮思考各自找到一个这样的地方：一条从未跑过的压缩路径，
> 和一组从不汇总的健康信号。
