## 二、「运行卡住 / 突然停止」

`turn/end` 的 `reason.kind === 'error'`、`error.code === 'UNKNOWN'` 共 12 次，
其 `assistant/attempt` 的 finish chunk 原文统一是：

```
web capture ended incomplete: incomplete     code: UNKNOWN
```

来源是 `browser-driver.js` 的

```js
if (!result.complete) throw new Error('web capture ended incomplete: ' + (result.reason || 'unknown'));
```

`complete` 由 `lib/decoder.js` 的 `DeepSeekStreamDecoder.finish()` 给出，旧判据是
「必须收到 `event: close` **且** `response.status === 'FINISHED'`」。真实网页在
长回答、页面切走、CDN 断流等情况下会**不发这一帧就断**，此时：

- 正文其实已经解码出来了（`onDelta` 已经吐给界面）；
- 工具调用可能已经完整（`<tool_call>{...}</tool_call>` 一整段都在）；
- 旧代码把它们**全部丢掉**并抛错。

对用户就是：字打到一半停住、工具不执行、需要手动再催一次。轨迹里
`e2e63eb6`（1093 事件、229 次调用）与 `8e9c538a`（164 次调用）各有一次这样的
收尾，都发生在长回答之后。

**已修**：解码器把「已解出的内容」带出来并把状态标成 `partial`（`reason:
stream_ended_before_finished`），驱动层在正文/思考/图片任一非空时接受这一轮，
记 `recoveredTurns` / `lastRecovered` 并在日志里明说，而不是扔进垃圾桶。
真正什么都没有（`partial: false`）或结构坏掉（`invalid_stream`）仍然失败。

## 三、工具调用失败的真实形态

按 `tool/result` 的 `isError` 统计，共 64 次工具报错，**全部**是这两类参数形状
问题，没有一次是工具本身执行出错：

| 报错原文 | 次数 | 真因 |
| --- | --- | --- |
| `invalid arguments: "offset" must be a number; "limit" must be a number` | 24+ | 网页把数字参数写成字符串（`"offset": "10"`） |
| `invalid arguments: "questions" must be an array` | 6 | `ask_user_question` 的数组被写成对象/字符串 |
| `invalid arguments: missing required property "description"` / `"command"` | 6 | 嵌套 schema 的必填项被漏掉 |
| `invalid arguments: "run_in_background" must be a boolean` / `"timeoutMs" must be a number` | 3 | 同上，类型漂移 |

这些错误本身是 Harness 正确拒绝（好事），但**网页模型看不到结构化 schema 的
类型约束有多硬**。同时 `e2e63eb6` 里还出现了另一种更隐蔽的：

```
助手消息里调用 write 工具（"name":"write"），而该会话只登记了 pwsh
```

——网页模型调了一个**本会话不存在**的工具。旧实现把这种调用静默过滤掉，
剩下的空回复被当成「收束」，任务从此不动（用户视角就是「跑着跑着不动了」）。

**已修**：解析出调用但**一个都不在本次工具表里**时抛 `TOOL_UNKNOWN`，错误文本
带上网页用的工具名与本会话可用工具名，作为这一轮结果回到会话——下一轮模型据此
改正形状，而不是让任务静静停住。# 附带把游标指纹从「工具对象整串 JSON」改成
「工具名集合」，避免描述措辞升级被判成上下文分叉（见第五节）。

## 四、「退出过一次 deepseek 后不管哪里都无法登录」

轨迹与代码对照后的结论是**两件事叠在一起**：

1. **界面只有一个入口，而且写死 deepseek。** 设置页「账户」那一行永远是
   `action('login', { siteId: 'deepseek' })`，其余站点没有登录入口。
2. **登录是 fire-and-forget。** `web-control.js` 旧实现：

   ```js
   loginTrigger(siteId).catch((err) => warn('login flow error:', err?.message));
   return { ok: true, message: '登录窗口打开中…' };
   ```

   立刻返回「成功」。真实失败（浏览器起不来、锁冲突、超时、窗口被关）只写进
   宿主控制台，界面永远显示未登录——用户感受就是「点了没反应，哪儿都登不上」。

3. 叠加一个具体的启动故障：Chromium 持久 profile 的**单实例锁**（`SingletonLock`
   / `SingletonCookie` / `SingletonSocket` / `lockfile`）在浏览器被强杀或上次启动
   中途失败后会留在 profile 里，下一次 `launchPersistentContext` 直接起不来。
   这是「退出过一次之后就登不上」最直接的可解释机制。

**已修**：

- `openLogin()` 返回 `{ok, loggedIn, alreadyLoggedIn, ms, note}`，并把
  `loginState` / `lastLogin` 暴露到驱动 status；
- `POST /__webcode/login` 默认**等**结果（`wait:false` 才回到旧行为），失败把原因
  一并回给界面；
- `launch()` 前置 `clearStaleProfileLocks()`（只在确认没有活着的 ctx 时清理），
  有头启动失败会清锁重试一次；
- 已经是登录态的 profile 直接返回「无需重复登录」，不再白开一次窗口。

## 五、「上下文为什么不会动」

两个原因，一个是游标指纹太敏感，一个是声明值太乐观：

1. `buildTurn` 的游标指纹把 `options.tools`（**整个对象**，含每条工具的描述文本与
   参数 schema）`JSON.stringify` 进去。宿主升级、描述措辞变化、schema 字段顺序变化
   都会让指纹变 → 游标被判为陈旧 → 下一轮走「整段重建」，网页侧被重开新会话。
   现象正是「上下文像不动」（每轮都在重建首轮）。
   **已修**：指纹只锁工具**名集合**（+ 模型 + 系统提示词 + 全局指令 + 已发消息）。
2. `resolveModel` 对每个站点都声明 `contextWindow: 1_000_000`。网页 composer 的真实
   上限远小于此，声明过大等于**告诉 DSH 永远不需要压缩**，transcript 只增不减。
   **已修**：按站点给保守值（DeepSeek 128k，其余 64k，可由
   `contextWindowBySite` 覆盖）；越界时仍由 `PROMPT_TRUNCATED` 回读校验报错，
   而不是静默截断。

## 六、「预览网页为什么除了 deepseek 都可以」

用 `lib/mirror.js` 直接对全部站点发起真实 HTTP 请求（`.tmp/tools/mirror-http-probe.mjs`，
2026-09-11 本机实测）：

| 站点 | 上游状态 | 说明 |
| --- | --- | --- |
| deepseek | **502 / 上游 403** | CloudFront：`Request blocked. We can't connect to the server for this app…` |
| glm | 200 | 正常 |
| kimi | 200 | 正常（484 KB 页面） |
| qwen | 200 | 正常 |
| grok | 200 | 正常 |
| zai（新增） | 200 | 正常 |
| doubao | 302 → `/chat/` | 镜像旧实现回写裸 `/chat/`，落在镜像命名空间之外 → 空壳 |
| chatgpt | 403 | 上游地区限制（页面自带说明） |
| claude | 403 | Cloudflare「Just a moment…」人机校验 |
| gemini | 502 | 本机网络不可达（桥的说明页） |

**真因**：镜像作为服务端反代去取 `chat.deepseek.com` 时被 CloudFront 判定为
机器人，返回 403 英文错误页；其它站点没有这层校验，所以「除了 deepseek 都能开」。

**已修**（三层）：

1. 镜像转发请求补上常规浏览器指纹（桌面 UA / Accept / Accept-Language /
   `sec-fetch-*`），并且**不再剥掉**浏览器真实发来的 `sec-fetch-*`；
2. 识别 CDN/WAF/网关错误页，替换成能自解释、能绕开的说明页（502 + 「改用独立
   窗口打开」按钮），不再把英文 403 原样透传；
3. 站内 302 重定向改写为 `mountPrefix + path`，留在镜像命名空间内（豆包根路径）。

面板侧：iframe 非 2xx 时在站点栏下方给一条明确提示与「改用独立窗口打开」按钮。

> 说明：即使补了指纹头，CloudFront 仍可能按本机出口 IP 直接拒绝（本次实测即是）。
> 因此这里不承诺「镜像一定打开」，而是保证**用户能看到为什么、并且有可用的替代
> 路径**（独立窗口走本机真实浏览器，不经反代）。
