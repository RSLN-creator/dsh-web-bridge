# 排查测试夹具数据漂移

## 输入
- 某测试预期断言失败（如 `includes('# xxx')`、`pattern` 未命中、`matches >= 1` 失败），但代码逻辑经独立验证正确。
- 现象通常是"测试里硬编码了工作区曾存在的文件名/标题/行内容"。

## 执行
1. 先独立复现，区分「逻辑错」还是「夹具过期」：
   ```bash
   node -e "const {readdirSync}=require('fs');console.log(readdirSync(process.cwd()).filter(n=>new RegExp('readme|plan','i').test(n)))"
   ```
2. 检查硬编码标记是否仍在工作区真实存在（grep 目标文件标题、list 目录）。
3. 用「真实存在的当前内容」替换硬编码标记：
   - 文件标题：`planText.split('\n').find(l => l.startsWith('#') && l.trim())`.
   - 搜索模式：换成必然命中的真实条目（如 `readme|plan`）而非已删除的 `risky`.
4. 断言从「查固定字符串」改查「从真实文件读出的当前值」，避免再次漂移。

## 环境依赖
- Node ≥ 20；测试用 node:test 或自写脚本。

## 常见陷阱
- 误区 A：把夹具漂移当成代码 bug，去改 src/preferred 逻辑，反而掩盖真回归。
- 误区 B：断言与取值不配套——改了 `planLine` 的取法却忘了改 `assert t2.includes(old)`.
- 陷阱 C：同一编辑批量提交时，前一个 hunk 的改动可能未真正落盘（读回来仍是旧值）；逐条 edit + 单独 verify。
