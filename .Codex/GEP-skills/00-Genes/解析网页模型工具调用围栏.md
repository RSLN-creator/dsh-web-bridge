# 解析网页模型工具调用围栏（<tool_call>）

## 输入
- 网页版 DeepSeek 被桥接成 DSH 的 LLM provider，需要把模型回复里的"工具调用"识别出来交给本地 harness 执行
- 症状：网页模型明明在一本正经地"调用工具"（输出标准围栏），但 harness 从不执行，工具 id 从未出现

## 执行
- 用**真实站点探针**确定网页模型真实输出格式，别靠猜。
  驱动真实站点发一条"请调用 pwsh 工具"的 prompt，抓原始返回：
  ```
  <tool_call>
  {"mcp_action": "call", "name": "pwsh", "purpose": "获取当前主机名称", "arguments": {"command": "hostname"}}
  </tool_call>
  ```
- 解析器必须同时接受三种围栏（模型/协议来回切换都不掉链）：
  1. ```` ```json … ``` ```` 代码块（webcode 协议）
  2. `<tool_call> … </tool_call>`（以及 `<function>` / `<stories>`，opplean / web-agent 风格）
  3. 散落在正文里的裸 `{"mcp_action":"call",…}` 对象
- 解析出的 call 字段：`name` 必须有且非空；参数取 `arguments ?? input ?? parameters`。

## 环境依赖
- `lib/agent-preset.js` 的 `parseAgentReply`（fence 扫描用非贪婪正则 + 去重 Set）

## 常见陷阱
- 旧实现只认 ```json → 网页模型一输出 `<tool_call>` 就被判"纯文字"，工具永不接入。这是"没分开没被识别"的真根因。
- preset 教的格式必须与解析器一致：真机贴合 `<tool_call>`，把 `<tool_call>` 定为推荐格式 A、```json 作为格式 B。
- preshop 里模型会紧跟工具调用补一句自然语言"我来查看…"——要容忍 prose 环绕围栏。
- 解析依赖 `options.tools` 的真实工具名做 `valid` 过滤：模型只会调 preset 列出的名字，别用不存在的工具名。
